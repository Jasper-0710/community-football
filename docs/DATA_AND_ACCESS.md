# 数据与权限基础说明

项目：中国社超上海赛区赛事平台。更新日期：2026-11-04。对应需求：#3、#11、#14、#18、#25。

本文件记录用户已确认规则及据此形成的基础设计。现有云端已验证用户建档、昵称和用户资料权限；后台认证已完成本地测试、真实云函数部署及8项认证检查，管理员集合权限已实测，首个账号已开通。网页经真实HTTP网关到云数据库的7项流程已通过。以下球队及报名数据结构属于后续方案。

头像沿用此前决定：暂不升级云套餐，客户端入口和云端头像写入保持关闭。球队队徽属于后续独立图片功能，仍需在开发时核验上传及访问方案。

## 管理员数据现状（D02）

首期采用 `adminAccounts/primary` 单文档，保存账号、PBKDF2密码记录、凭据版本、限流计数及最多5个会话摘要；不另建 `adminSessions`。数据库事务维护登录、失败锁定和退出撤销。客户端直接读写必须全部关闭，权限实测通过前不导入账号。

密码使用PBKDF2-HMAC-SHA256、600,000次迭代和随机盐；随机会话令牌仅将SHA-256摘要保存到数据库，固定8小时到期。后台通过独立会话校验，不信任微信用户角色或浏览器存储中伪造的管理员信息。准确字段和接口见 [adminAuth说明](../cloudfunctions/adminAuth/README.md)。本地测试已通过，云端验证进度见开发日志。

## 后续数据结构草案

字段名为技术方案，尚未创建相应集合。每个功能实施时补充精确字段类型、索引、状态转换和输入边界；业务规则未确认的部分不硬编码。

| 拟用集合 | 主要字段 | 关联与约束 |
| --- | --- | --- |
| teams | _id、leaderUserId、name、district、badgeFileId、description、createdAt、updatedAt | leaderUserId引用users；一个领队仅管理一支球队；队徽存文件引用，临时链接不作为永久字段 |
| leaderTeamBindings | _id=用户ID、teamId | 以用户ID作为唯一键，建队事务内占用，防止并发创建多队；仅服务端维护 |
| players | _id、teamId、name、number、position、createdAt、updatedAt | 球员归属teams；号码范围、重号及位置选项在表单与报名规则阶段落实 |
| competitions | _id、name、description、format、displayEnabled、registrationEnabled、registrationStartAt、registrationEndAt | 展示与报名开关独立；赛制、队伍名额及报名限制按后续确认配置 |
| registrations | _id、competitionId、teamId、submittedBy、rosterSnapshot、status、createdAt | 关联赛事及球队，保留报名时球员快照；状态、撤销及修改规则待确认 |
| matches | _id、competitionId、stage、round、groupId、homeTeamId、awayTeamId、scheduledAt、venue、status、scores、stats、revision | 分组与轮次属于赛事，不作为球队固定属性；前后轮签位随赛制实现 |
| matchEvents / resultRevisions | matchId、teamId、playerId、kind、minute、revision及变更记录 | 记录进球助攻红黄牌换人；改分恢复与统计使用相同有效版本；细节随赛果功能实施 |
| articles | _id、category、title、coverFileId、body、published、pinned、publishedAt | 五类内容及发布状态服务首页、列表与搜索 |
| favorites | userId、teamId、createdAt | 用户与球队关联唯一，用于后续跨设备收藏 |

当前 `src/domain/types.ts` 是演示展示模型，不能直接当作生产集合：例如球队固定A/B分组、五个导航和原型新闻分类均仍需按已确认需求改造。接入时通过数据层映射，保持各页面读取同一份业务结果。

## 权限约定与建队流程

| 身份 | 可执行操作 | 服务端依据 |
| --- | --- | --- |
| 游客 | 读取允许公开的赛事、新闻、赛程、赛果及榜单 | 公开查询接口和展示状态；不直接开放业务集合读写 |
| 普通微信用户 | 读写本人已开放资料，按规则创建一支球队 | 微信可信身份及本人用户ID；拒绝传入角色或冒充他人 |
| 球队领队 | 管理本人球队及球员，提交本人球队报名 | 根据团队归属校验；仅有role=leader不足以操作任意球队 |
| 后台管理员 | 执行已开放的后台管理操作 | 独立后台账号及有效会话；微信资料中的admin字符串不自动产生后台会话 |

建队实施顺序：校验微信身份及资料 → 事务读取本人绑定 → 无球队时创建球队、写入唯一绑定并更新领队身份 → 事务成功后返回。事务失败时不能只留下领队身份或孤立球队；重试返回已建队或明确冲突，不创建第二支球队。

管理员代建球队、球队转让/解散后能否重建、每人终身或同时管理上限等生命周期细节尚未确认。当前仅落实用户明确的“一名领队管理一支球队”，不推导额外删除或转移权限。
