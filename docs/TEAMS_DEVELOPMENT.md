## 已确认表单规则

| 内容 | 规则 |
| --- | --- |
| 领队 | 建队成功自动取得身份，每人管理1支球队；建队前须有昵称 |
| 球队 | 队名、上海所属区、领队联系电话必填；介绍选填 |
| 球员 | 姓名、球衣号码、位置必填；号码1–99，同队当前名单内不能重复 |
| 位置 | 门将、后卫、中场、前锋 |
| 队徽 | 用户同意当前使用默认图案，图片上传待云存储环境配置；需求保留 |

实现的输入边界：队名最多40个Unicode码点，球队介绍500字，球员姓名30字；电话支持手机号、座机和国际区号，实际数字7–15位。上述长度及电话格式是技术校验边界。控制字符、伪造归属、角色、服务端字段和任意图片地址不接受。联系电话仅返回本人和授权后台管理员。

## 数据及接口

所有集合禁止客户端直接读写，使用 `{ "read": false, "write": false }`。继承现有 `users` 和 `adminAccounts` 私有权限，新增以下集合：

| 集合 | 主键与用途 | 一致性约束 |
| --- | --- | --- |
| teams | 首次为`t_` + 用户ID，重建为`t_` + sha256(用户ID:创建请求ID)；球队资料、领队ID、当前roster、version、创建请求指纹及时间 | 当前名单嵌入球队文档，最多99个唯一号码；读详情获得一致快照 |
| leaderTeamBindings | 用户ID；保存唯一teamId，解散后为null并记录lastTeamVersion/lastDissolution | 与球队创建、users角色/电话在同一事务提交，防并发创建第二队 |
| players | `p_` + 32位随机请求标识；球队ID、姓名、号码、位置、状态和时间 | 与teams.roster同事务更新；移出后保留removed档案，不硬删除 |

用户ID沿用 `sha256(APPID + ':' + OPENID)`，身份只由微信可信上下文取得。领队写接口不接收目标teamId，通过本人绑定查找球队；已有leader角色不授予跨队操作权限。创建请求用指纹幂等处理；资料修改和球员操作校验球队version。存储失败整体回滚；相同球员操作重试不重复写入。

云函数 `teamManagement` 使用微信 `wx.cloud.callFunction`：

| action | 输入 | 结果 |
| --- | --- | --- |
| mine | 无 | 本人球队及当前名单，未建队为null |
| create | requestId、form | 创建球队/绑定/领队身份；不覆盖既有球队 |
| update | expectedVersion、form | 更新本人球队资料及用户联系电话 |
| savePlayer | expectedVersion、id、form | 新增或更新球员，校验号码唯一及归属 |
| removePlayer | expectedVersion、id | 移出当前名单，保留历史球员档案 |

后台复用 `adminAuth` 的HTTPS网关和有效管理员Bearer会话：`teams.listAdmin`（20条分页，支持cursor）及 `teams.getAdmin`（id）。返回投影不含OPENID、用户ID、创建指纹或绑定信息。D04后台档案只读；管理端增改删、能力值、历史报名/赛程/成绩关联约束仍按 #18 后续任务推进。11/5追加领队解散功能，见下文；球队转让及后台代建仍未开放。

前端遇到网络失败、返回数据异常或版本冲突时，要求重新读取后继续；失败读取清除旧资料。球员移出有二次确认；取消不改数据。历史档案保留不等于已实现报名历史快照，D05必须保存当时参赛名单。

## D04-追加：解散球队（11月5日）

用户已同意补充领队解散功能。入口位于“我的 → 我的球队”页面底部的“球队管理”。先检查条件，再展示确认卡片，必须输入完整队名才能确认；取消不写数据。解散后小程序回到可建队状态，后台保留“已解散”档案、解散时间、领队昵称快照及解散时球员名单。

实现 `checkDissolution(expectedVersion)` 只读检查和 `dissolve(expectedVersion,confirmName)` 事务操作。后者重新检查归属、版本、名称和业务关联，将球队status设为dissolved，释放绑定并恢复普通用户身份（admin身份保留），不物理删除teams/players。原球队不能从当前界面恢复或编辑。已有记录缺少status时视为active。

首次球队ID兼容原数据，重建使用新的请求派生ID；创建请求不可复用。绑定保留最后版本，重建版本继续递增，防旧页面的更新/添加球员/解散请求作用到新球队。重复解散在尚未重建时幂等成功，重建后旧请求被拒绝。

关联扫描包括registrations.teamId、matches.homeTeamId/awayTeamId、matchEvents.teamId、resultRevisions.teamId/homeTeamId/awayTeamId；任何状态的关联（包括撤销报名）均阻止解散，以保留历史。未建设集合仅在明确的-502005不存在错误时视为空；权限、网络和其他错误均中止。当前这些关联模块尚未实施，扫描及阻止行为已用隔离测试数据验证，不能称为完整报名/赛程/赛果云端联调。

**后续D05–D08写入契约：** 创建或修改报名、赛程、事件、赛果引用时，必须在同一数据库事务内读取相关teams，确认active，并递增其version后写入引用；多队比赛逐个处理所涉及球队。关联扫描通过普通数据库查询执行，事务中的球队文档读写作为与新增引用操作的并发冲突点。不得仅查询球队后在事务外写入引用；新增字段或引用集合时同步扩展references.js及测试。球员档案的active表示解散时在名单内，使用球员前还须检查所属球队状态。禁止硬删赛程来绕过已有成绩关联。
